# L068 小さなページは開けるが、大きなファイルのダウンロードだけ止まる

1. client01（ops、管理操作は sudo）で、転送サイズで症状が変わるかを切り分ける
   - `curl -s -m 5 -o /dev/null -w '%{http_code} %{size_download}\n' http://web01/index.html` と、同じ形で large.bin を取得する
   - 小さいページは取れて、大きいファイルだけが途中で止まるかを確かめる

2. 経路の各区間の MTU を確かめる
   - client01・gw01・web01（いずれも ops）で `ip -o link show` を実行し、インターフェイスごとの mtu を書き出す
   - gw01 は社内側と社外側の 2 つのネットワークインターフェイスを持っている点に注意する

3. 経路を通れるパケットの大きさを測る
   - web01（ops）から client01 へ、`ping -M do -s <サイズ> -c 2 -W 2` でサイズを変えて送る
   - 通るサイズと通らないサイズの境目を探し、「Frag needed」のような通知が返るかも見る

4. 大きいパケットがどこで消えるかを確かめる
   - gw01（ops）で `sudo tcpdump -i any -n tcp port 80` を取りながら、client01 から large.bin を取得する
   - 社内側に入ったパケットが、社外側から出ていくかを見る

5. 対処のあとで、client01 から large.bin と index.html の両方を取り直す

## なぜそこを疑うか

接続が成立し、小さな応答は届くのに大きな応答だけが止まるときは、通信の可否ではなく、パケットの大きさを疑います。
経路の途中に MTU の小さい区間があり、そのことが送信側に伝わらないと、大きなパケットだけが黙って捨てられます。
エラーが出ないのはそのためで、サイズを変えた ping で境目を見つけると原因がはっきりします。

## つまずきやすい点

- 疎通確認を小さな ping や小さいページだけで済ませ、「経路は正常」と判断すること
- ゲートウェイの社外側の MTU を変えて辻褄を合わせること。経路の実際の MTU を偽ることになり、完了条件で禁じています
- tracepath や `ip route get` はこの環境では使えないことがあります。サイズを変えた ping で測ってください
- ネットワークの設定変更は、この環境では許された書き方に限られます。`nft` は受け付ける書き方が限られており、拒否されても権限の問題とは限りません。`ip`・`iptables`・`sysctl` で許される範囲も確かめてください
