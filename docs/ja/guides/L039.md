# L039 注文した直後の履歴に、その注文が出ない

1. 構成を把握する
   - 書き込みは主（db01）、参照は複製（db02）に分かれている
   - app01（ops、管理操作は sudo）の /etc/shop/app.conf で、書き込み直後の参照がどちらの DB に向いているかを見る

2. db02（ops）で複製の状態を確認する
   - `sudo mariadb -e 'SHOW SLAVE STATUS\G'` の Slave_IO_Running・Slave_SQL_Running と Seconds_Behind_Master を読む
   - 何度か実行して、遅れが縮んでいるのか増え続けているのかを見る

3. 遅れの理由を、主と複製の両方から探る
   - db01（ops）で `sudo mariadb -e "SHOW GLOBAL STATUS LIKE 'Com_insert'"` を数秒あけて 2 回実行し、その差からどの程度の書き込みが続いているかを見る（一つひとつの INSERT はすぐ終わるので、SHOW FULL PROCESSLIST にはほとんど現れない）
   - 書き込み先のテーブルが分かれば、`SELECT COUNT(*)` を時間をあけて比べても増え方が分かる
   - db02（ops）で `sudo mariadb -e 'SHOW VARIABLES'` を実行し、複製の適用に関わる設定を確認する

4. 対処のあとで、もう一度 db02 の遅れと両スレッドの状態を確認する
   - 遅れが 0 付近まで下がり、IO・SQL スレッドがどちらも Yes のままであること

## なぜそこを疑うか

「数秒後に再読み込みすると出る」のは、データが消えたのではなく、届くのが遅れているという症状です。
書き込みと参照で接続先が違う構成では、まず両者の間の時間差（複製の遅れ）を疑います。
遅れが一時的なものか、書き込みの量に適用が追いつかず増え続けているのかで、手を入れる場所が変わります。

## つまずきやすい点

- 複製を止めたり作り直したりして遅れを消そうとすること。完了条件はレプリケーションが動き続けていることも見ています
- 複製側の設定には、複製を止めないと変えられないものがあります。エラーを読み、順序を考えてから実行してください
- 実行中の値だけを変えて、設定ファイルに残さないこと。再起動すると元に戻ります
- 遅れの解消だけで済ませ、書き込み直後の参照をどこへ向けるかを考えないこと
