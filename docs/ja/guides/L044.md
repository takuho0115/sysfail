# L044 外部 API の呼び出しが失敗する

1. app01（ops、管理操作は sudo）で、失敗の出方を確かめる
   - `curl -s -o /dev/null -w '%{http_code}\n' -m 3 -x http://nat01:3128 http://partner01/ping` を何回か実行する
   - 毎回失敗するのか、ときどき失敗するのかを見る

2. 外へ出る通信がすべて通る場所（nat01）の状態を見る
   - toolbox（player）で `cloud nat get-nat-gateway-statistics --nat-gateway-id nat01`、または nat01（ops）で `natctl stats nat01` を実行する
   - ポートの総数・使用数・使用率と、port_exhausted の値を読む

3. 時間をおいてもう一度 stats を取る
   - port_exhausted が増え続けているか、使用率が上限に張り付いていないかを比べる

4. nat01（ops）で、閉じた接続がどれだけ残っているかを見る
   - `ss -s` の timewait の数を確認する

5. 対処のあとも stats を何回か取り、使用率が下がって port_exhausted が増えなくなったことを確かめる
   - 管理コマンドの使い方は、`cloud nat help` や、`natctl` を引数なしで実行すると表示される

## なぜそこを疑うか

特定の相手ではなく、外へ出る通信全般が断続的に失敗する場合は、相手側ではなく通り道で共有している資源を疑います。
NAT は外向きの接続ごとに送信元ポートを割り当てるので、接続を次々に張る使い方ではポートが足りなくなります。
閉じた接続のポートもしばらく使えないため、要求の量が多くないように見えても枯渇が起きます。

## つまずきやすい点

- 相手側の API の不調だと決めつけて、partner01 だけを調べようとすること
- 一度だけの stats で判断すること。増え方を見るには、間をおいて 2 回以上取る必要があります
- OS のポート範囲やタイムアウトを変えようとすること。この環境では NAT 側の資源を見直すのが筋です
