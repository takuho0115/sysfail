# L024 注文確認メールが届かない

1. mq01（ops、管理操作は sudo）でキューの状態を見る
   - `mqctl -p /mail list_queues name messages consumers`（`sudo` は付けない。付けると接続先の指定が消える）
   - 件数が増えているか、コンシューマー（consumers）がいくつ接続しているか
   - 「cloud01 に接続できません」と出る場合は、キューの模擬サーバーが mq01 自身で動いているので、`SIM_CLOUD_URL=http://mq01:8500 mqctl -p /mail list_queues name messages consumers` と接続先を指定する（この環境の既知の不具合）

2. コンシューマーが 0 なら、消費する側の worker01（ops）に移る
   - `systemctl status mail-worker` で動いているか、再起動の上限に達していないか
   - `journalctl -u mail-worker -n 20 --no-pager` で接続の失敗の文面を読む

3. ワーカーの設定ファイルを探して、接続先の値を読む
   - ユニットや起動するプログラムから、読んでいる設定ファイル（/etc/mailworker/ の下）をたどる

4. ログに出た接続先の名前と、キューサーバーに実在する名前を比べる

5. 直したらワーカーを再起動し、mq01 で件数が減っていくことを確かめる

## なぜそこを疑うか

メールが届かずキューのメモリ使用量が増えているのは、メッセージが入るのに出ていかないためです。
コンシューマーが 0 なら、キューではなく取り出す側が接続できていません。接続できない理由はワーカーのログに出ます。

## つまずきやすい点

- メモリを下げるためにキューを空にすること（メールが失われる。完了条件で禁止）
- ワーカーが再起動の上限に達して止まっている場合、設定を直しても `restart` だけでは起動しないことがある（`systemctl reset-failed` を挟む）
- ログの名前と設定の名前が一文字違いのように似ていて、見比べずに見落とすこと
