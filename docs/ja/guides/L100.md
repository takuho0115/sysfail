# L100 全システムが同時に不調である

1. front01（ops、管理操作は sudo）で、何も変えずに現状を把握する
   - 現在時刻の表示、`recover-status`、`step-check`、`curl -s -m 3 -o /dev/null -w '%{http_code}\n' http://localhost/`
   - app01・db01 にも toolbox（左のペイン）から ssh で入り、サービス・通信・メモリ・データの状態を同じように見る

2. db01（ops、sudo）で、データの状態と「失うと戻らないもの」を探す
   - `aggregate --verify` を何度か実行し、結果が正しいか、毎回同じ結果になるかを確かめる
   - `lsmem --all` のアドレス範囲を調べ、`sudo memtester -p <開始アドレス> 16M 1` で領域ごとの結果を比べる。`edac-util -v` がコントローラーを検出しない場合は、領域ごとの試験で不良箇所を絞り込む
   - `mount` と `ls /var/lib/recovery` で、復旧の台帳が消えやすい場所（メモリ上）に置かれていないかを見る

3. 何かを変える前に、db01（ops、sudo）で台帳を保全する
   - 永続する場所へコピーし、コピーできたことを確かめる

4. 通信の瞬断を解消する
   - ルーター（net01）には ssh できないので、front01（ops）から `sudo sf-console net01 help` または `sudo sf-console net01 ?` で管理コンソールのコマンドを調べ、`show running-config`・`show interfaces`・`tc qdisc show` の結果を照合する。不要なキュー規則は `tc qdisc del dev <IFACE> root` で削除する
   - 瞬断の間はコンソールにもつながらない。つながるまで待ってコマンドを送り直す

5. アプリの起動に必要なものをそろえる
   - app01 のアプリが何に接続できずに止まるのかを確かめ、管理コンソールの `show services` で管理先を確認し、front01（ops）の `cloud help`・`cloud license help` で対応する機能を探す（`sudo` を付けると接続先の指定が消えて「接続できません」になるので、付けない）

6. db01（ops、sudo）で、不良のメモリバンクを無効化し、集計が正しくなったことを確かめる
   - `sudo chmem -d -b <ブロック番号>` で使用停止にし、`lsmem`・`free --mebi`・`numactl -H` を確認したあと `aggregate --verify` を再実行して確かめる

7. 各ホストで `step-check` を実行して順序を確かめてから、復旧手順を 1 つずつ実行する
   - 実行前に `stepNN --check` で実行できる状態かを確かめ、`sudo stepNN` で実行する（`sudo /opt/recover/stepNN` も使える）
   - 最後に front01 で `curl` を 10 回続けて、すべて 200 が返ることを確かめる

## なぜそこを疑うか

同時多発の障害では、目についた順に直すと、不可逆な操作で取り返しがつかなくなります。
まず変更しない観察で全体を把握し、「失うと戻らないもの」を先に守ります。
そのうえで、他の問題の原因になっている土台（通信、ライセンス、ハードウェア）から順に片づけます。
集計の値が毎回おかしいときは、データそのものより、データを読む経路（メモリなど）を疑います。

## つまずきやすい点

- 壊れて見えるデータファイルを直接書き直すこと。原因が読み取りの経路にあれば、直しても再び壊れる
- 保全の前にメモリバンクを止めたり再起動したりすること
- 瞬断の最中に送ったコマンドが失敗したのを、コマンドの誤りと取り違えること
- 復旧手順を `--check` なしで進めること
