# PF-19 ゲーム用イメージ {#pf-19}

`sysfail doctor` の PF-19 の項目の説明です。doctor は 1 行の要点とこのページの URL を出します。

## まだ取得していない {#missing-fetch}

公式の sysfail は、レベル環境に使うイメージ（el9・toolbox）を、実行ファイルに埋め込まれた digest を指定して ghcr.io から取得します。最初の play で自動で取得します。先に `sysfail doctor --build` で取得しておくと、プレイの前に準備が済みます。取得は初回だけで、約 450MB をダウンロードし、展開後は docker のデータ領域を約 2GB 使います。

取得したイメージは、ID とラベルが実行ファイルに埋め込まれた値と一致するときだけ使います。同じ名前の別のイメージがあっても使わず、取得し直します。

## レジストリに接続できない {#fetch-network}

ghcr.io に接続できませんでした。インターネットにつながるか、DNS で名前解決ができるか（`getent hosts ghcr.io`）を確かめてから、`sysfail doctor --build` をやり直してください。インターネットにつながらない端末では、別の端末で取得して `docker save`・`docker load` で持ち込めます（README の「ゲーム用イメージを取得できない（PF-19）」）。

## プロキシで止まった {#fetch-proxy}

イメージを取得するのは docker デーモンです。プロキシは `~/.docker/config.json` ではなく、デーモン側に設定します。Linux では `/etc/systemd/system/docker.service.d/http-proxy.conf` に `HTTP_PROXY`・`HTTPS_PROXY`（必要なら `NO_PROXY`）を書き、`sudo systemctl daemon-reload` と `sudo systemctl restart docker` の後で `sysfail doctor --build` をやり直してください。Docker Desktop では設定画面の Resources → Proxies で設定します。

## 取得回数の制限 {#fetch-ratelimit}

短い時間に取得を繰り返したため、ghcr.io が取得を制限しました（429・toomanyrequests）。しばらく時間を置いてから `sysfail doctor --build` をやり直してください。

## 公開先にイメージがない {#fetch-notfound}

このバージョンの sysfail が指定する digest のイメージが ghcr.io にありませんでした。公開の準備が終わる前のバージョンか、イメージが削除された可能性があります。最新のバージョンの sysfail を入れ直すか、GitHub Issues で知らせてください。

## 公開先で拒否された {#fetch-auth}

ghcr.io が取得を拒否しました（401・403）。docker が別のアカウントで ghcr.io にログインしていて、そのアカウントにはイメージを読む権限が無いことがあります。`docker logout ghcr.io` を実行してから `sysfail doctor --build` をやり直してください。それでも拒否されるときは、GitHub Issues で知らせてください。

## 取得したイメージが想定と違う {#fetch-mismatch}

取得したイメージの ID かラベルが、実行ファイルに埋め込まれた値と一致しなかったため、使わずにタグを外しました。取得し直しても同じイメージを取得するだけなので、手動で取得するコマンドは表示しません。GitHub Issues で知らせてください。

## 開発用のビルド {#nosource}

ソースからビルドした sysfail には、取得するイメージの digest が埋め込まれていません。リポジトリのルートを `--assets-dir` に渡して、イメージを手元でビルドしてください（例: `sysfail --assets-dir . doctor --build`）。

---

`--assets-dir` に images/ のあるディレクトリを渡したときは、今までどおり手元でビルドします。以下はその場合の項目です。

## まだビルドしていない {#missing}

レベル環境に使うイメージは、最初の play で自動でビルドします。先に `sysfail doctor --build` でビルドしておくと、ビルドのときに起きる問題を、プレイの前に確かめられます。ビルドは初回だけで、5〜20 分かかり、約 4GB の空きが要ります。

## パッケージを取得できない {#network}

ビルドの途中で、インターネットからパッケージを取得できませんでした。次を確かめてから `sysfail doctor --build` をやり直してください。

- インターネットにつながるか
- DNS で名前解決ができるか（`docker run --rm alpine nslookup dl-cdn.alpinelinux.org`）
- プロキシが要る環境では、docker デーモンにプロキシを設定しているか（`/etc/systemd/system/docker.service.d/` の `HTTP_PROXY`・`HTTPS_PROXY`）

## 空き容量の不足 {#capacity}

ビルドには docker のデータ領域に 6GB 以上の空きが要ります。`docker system df` で使用量を確かめ、使っていないイメージやコンテナを消してから（[PF-08](pf-08.md#low)）、`sysfail doctor --build` を実行してください。

## ビルド用のネットワークを作れない {#netfilter}

docker がビルド用のネットワークを作れませんでした。主な原因は、カーネルモジュールの不足です。

1. 次のモジュールが読み込まれているかを `lsmod` で確かめます: `ip_tables`・`iptable_nat`・`iptable_filter`・`xt_addrtype`・`xt_conntrack`・`br_netfilter`・`veth`
2. 足りないものを読み込みます（例: `sudo modprobe -a ip_tables iptable_nat iptable_filter xt_addrtype xt_conntrack br_netfilter veth`）。
3. docker を再起動します（`sudo systemctl restart docker`）。
4. `sysfail doctor --build` をやり直します。

firewalld を使っている場合は、docker ゾーンがあるかも確かめてください（`sudo firewall-cmd --get-zones`）。

## docker デーモンに接続できない {#daemon}

ビルドの途中で docker デーモンとの接続が切れました。デーモンが動いているかを確かめてから（[PF-02](pf-02.md#down)）、`sysfail doctor --build` をやり直してください。

## 時間切れ {#timeout}

ビルドが時間内に終わりませんでした。回線が遅いときや、docker がほかの作業で混んでいるときに起きます。並行する作業が終わってから `sysfail doctor --build` をやり直してください。

## その他の失敗 {#other}

画面に出ている docker build の出力の最後の数行に、失敗の理由が出ています。それを確かめてから `sysfail doctor --build` をやり直してください。解決しないときは、その数行を添えて GitHub Issues で知らせてください。
