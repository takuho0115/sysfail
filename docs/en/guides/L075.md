# L075 Handshakes fail from a legacy TLS client

1. On gw01 (ops; use sudo for administrative operations), read the nginx error log
   - Use `sudo grep -iE 'handshake|cipher' /var/log/nginx/error.log` to identify the stage at which the partner's connection fails
   - Distinguish "no shared cipher" from certificate or protocol failures

2. On gw01 (ops), check how nginx chooses its ciphers
   - In the TLS configuration, see whether `ssl_ciphers` follows the OS policy through PROFILE=SYSTEM

3. On gw01 (ops), check the current OS crypto policy and available ciphers
   - `update-crypto-policies --show`
   - `openssl ciphers -v PROFILE=SYSTEM | head`
   - Identify which ciphers the hardening removed

4. On gw01 (ops), reproduce the partner's cipher choices
   - Run `sfclient` without arguments to list profiles, then connect to `https://gw01/` using a profile close to the older client. If certificate verification fails, add `--insecure` to distinguish it from a cipher failure

5. Find a way to add only the missing cipher without undoing the hardening
   - Inspect the modules under `/usr/share/crypto-policies/policies/modules/`
   - After the change, restart nginx and test both the connection from step 4 and a regular client

## Why investigate this area?

If only older peers fail after hardening, they likely require something the hardening removed.
"No shared cipher" in the error log means that the two sides have no overlap in the ciphers they offer.
If nginx follows the OS policy, investigate the OS policy rather than nginx's own cipher selection.

## Common pitfalls

- Adding ciphers based on guesses without checking the partner's choices. Reproduce the failure with an `sfclient` profile first
- Reverting the policy to DEFAULT or LEGACY, undermining the audit requirements
- Applying a module without checking whether its specification adds to or replaces the current selection
- Forgetting to restart nginx after applying the change
