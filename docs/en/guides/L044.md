# L044 Calls to external APIs are failing

1. On app01 (ops; use sudo for administrative operations), examine the pattern of failures
   - Run `curl -s -o /dev/null -w '%{http_code}\n' -m 3 -x http://nat01:3128 http://partner01/ping` several times
   - Does it fail every time, or only intermittently?

2. Inspect nat01, the point all outbound traffic passes through
   - On toolbox (player), run `cloud nat get-nat-gateway-statistics --nat-gateway-id nat01`, or run `natctl stats nat01` on nat01 (ops)
   - Read the total ports, ports in use, utilization, and port_exhausted value

3. Collect stats again after a short interval
   - Check whether port_exhausted keeps rising and whether utilization stays at its limit

4. On nat01 (ops), check how many closed connections remain
   - Check the timewait count in `ss -s`

5. After taking action, collect stats several more times to confirm that utilization has fallen and port_exhausted has stopped increasing
   - For management command usage, run `cloud nat help` or `natctl` without arguments

## Why investigate this area?

If outbound traffic fails intermittently across destinations rather than for one specific peer, suspect a shared resource on the path instead of the remote systems.
NAT assigns a source port to each outbound connection, so workloads that continually open new connections can exhaust the available ports.
Ports from closed connections also remain unavailable for a while, so exhaustion can occur even when the request volume does not seem high.

## Common pitfalls

- Assuming the partner API is unhealthy and investigating only partner01
- Judging from a single stats snapshot. To see growth, take at least two measurements separated by an interval
- Trying to change OS port ranges or timeouts. In this environment, review the resources on the NAT side
