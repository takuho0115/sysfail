# L039 A new order is missing from the order history right after it is placed

1. Understand the architecture
   - Writes go to the primary (db01), while reads go to the replica (db02)
   - On app01 (ops; use sudo for administrative operations), check /etc/shop/app.conf to see which DB receives reads immediately after a write

2. On db02 (ops), check replication status
   - Read Slave_IO_Running, Slave_SQL_Running, and Seconds_Behind_Master from `sudo mariadb -e 'SHOW SLAVE STATUS\G'`
   - Run it several times to see whether the lag is shrinking or continuing to grow

3. Investigate the reason for the lag on both the primary and the replica
   - On db01 (ops), run `sudo mariadb -e "SHOW GLOBAL STATUS LIKE 'Com_insert'"` twice, a few seconds apart. Use the difference to gauge ongoing write volume (individual INSERTs finish quickly, so they rarely appear in SHOW FULL PROCESSLIST)
   - If you know the table receiving writes, comparing `SELECT COUNT(*)` over time also shows its rate of growth
   - On db02 (ops), run `sudo mariadb -e 'SHOW VARIABLES'` and inspect settings related to applying replication events

4. After taking action, check db02's lag and both thread states again
   - The lag should fall close to 0, with both the IO and SQL threads remaining Yes

## Why investigate this area?

Data appearing after a refresh a few seconds later suggests delayed arrival rather than lost data.
When writes and reads use different destinations, start by investigating the delay between them: replication lag.
A temporary delay and a backlog that keeps growing because replay cannot keep up with writes call for investigation in different places.

## Common pitfalls

- Trying to eliminate lag by stopping or rebuilding replication. The completion conditions also check that replication keeps running
- Some replica settings can only be changed while replication is stopped. Read the error and plan the sequence before acting
- Changing only runtime values without saving them in the configuration file. They will revert after a restart
- Addressing only the lag without considering where reads immediately after writes should go
