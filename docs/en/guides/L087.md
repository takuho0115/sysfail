# L087 The daemon starts and then exits

1. On mw01 (ops; use sudo for administrative operations), check the service status and how it exits
   - Use `systemctl status vendord` to distinguish an abnormal termination from a normal exit (exit code 0)
   - Also check whether the unit file is configured to discard output

2. On mw01 (ops), start it manually and inspect the exit code
   - `/opt/vendor/vendord; echo "exit=$?"`

3. On mw01 (ops, sudo), observe its behavior externally
   - `strace -f -e trace=network,openat /opt/vendor/vendord`
   - Read which host and port it tries to connect to, and which file it opens after the failure

4. On mw01 (ops), check whether the destination really is unavailable
   - Use `ss`, `nc`, or similar tools to see whether that host and port respond
   - If you cannot fix the destination, investigate the file opened in step 3 and the supplied tool that handles it

5. On mw01 (ops), find and read the internal runbook
   - Look under `/srv/runbook` for procedures covering an unavailable destination
   - Use only the documented official procedure, start vendord, and check port 7000 and the status display on app01

## Why investigate this area?

A program that exits silently with code 0 has often decided for itself that its prerequisites are not met.
When logs are unavailable, observing system calls externally reveals what it tried to check and what failed.
This observes behavior rather than analyzing the program's internals, so it stays within the contractual restrictions.

## Common pitfalls

- Assuming that no logs means there is no way forward. strace lets you observe externally
- Focusing only on the failed connection and missing the file opened immediately afterward
- Modifying the program binary or bypassing the problem with a method absent from the runbook
