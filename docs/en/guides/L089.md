# L089 The order of the recovery steps is unclear

1. On db01 (ops; use sudo for administrative operations), assess the current state without changing it
   - Use `recover-status` to inspect the current stage and consistency
   - Use `sudo mariadb` to check order counts and total amounts, and identify what is missing

2. On db01 (ops), read every runbook fragment
   - Read the fragments under `/srv/runbook` and make a table of the stage each step requires and the stage it produces
   - The numbers in fragment filenames do not indicate execution order

3. On db01 (ops, sudo), try every step in check-only mode
   - Run `/opt/recover/stepNN --check` for all 20 steps
   - Check for discrepancies with the table from step 2 and establish the execution order

4. Once the order is established, execute one step at a time on db01 (ops, sudo)
   - Ensure execution stops on failure, and inspect `recover-status` along the way
   - At the end, verify the stage, counts, and totals

## Why investigate this area?

When the wrong order can cause irreversible damage, gather each step's prerequisites through checks that do not change state before executing anything.
Arrange fragmented instructions by their prerequisites and results, rather than their file order, to determine the sequence.

## Common pitfalls

- Executing fragments in filename order
- Running `--check` on only some steps and guessing the rest
- Using a loop that continues to the next step after a failure
- Misreading the cause of a failure because you forgot `sudo`; the state files and DB require root privileges
