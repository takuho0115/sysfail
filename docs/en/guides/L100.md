# L100 Every system is failing at once

1. On front01 (ops; use sudo for administrative operations), inventory the current state without changing anything
   - Check the current time display, `recover-status`, `step-check`, and `curl -s -m 3 -o /dev/null -w '%{http_code}\n' http://localhost/`
   - Connect to app01 and db01 via ssh from toolbox (the left pane) and similarly inspect services, connectivity, memory, and data

2. On db01 (ops, sudo), inspect the data and identify anything that cannot be recovered if lost
   - Run `aggregate --verify` several times to see whether the results are correct and consistent
   - Inspect the address ranges from `lsmem --all` and compare results for each region with `sudo memtester -p <開始アドレス> 16M 1`. If `edac-util -v` detects no controller, narrow the problem down through tests of individual regions
   - Use `mount` and `ls /var/lib/recovery` to check whether the recovery ledger is stored somewhere volatile, such as memory

3. Before changing anything, preserve the ledger on db01 (ops, sudo)
   - Copy it to persistent storage and verify that the copy remains available

4. Stop the intermittent network interruptions
   - The router (net01) cannot be accessed via ssh. From front01 (ops), inspect management console commands with `sudo sf-console net01 help` or `sudo sf-console net01 ?`, then compare the output of `show running-config`, `show interfaces`, and `tc qdisc show`. Remove unnecessary queue rules with `tc qdisc del dev <IFACE> root`
   - The console is also unreachable during an interruption. Wait until it is reachable and retry

5. Satisfy the application's startup prerequisites
   - Find what app01 cannot connect to during startup. Check managed destinations with the console's `show services`, then look for the corresponding features using `cloud help` and `cloud license help` on front01 (ops). Do not add `sudo`: it removes the destination setting and causes a connection failure

6. On db01 (ops, sudo), disable the faulty memory bank and check that aggregation becomes correct
   - Disable it with `sudo chmem -d -b <ブロック番号>`, inspect `lsmem`, `free --mebi`, and `numactl -H`, then check `aggregate --verify` again

7. On each host, use `step-check` to confirm the order before executing recovery steps one at a time
   - Before execution, use `stepNN --check` to confirm the prerequisites, then run `sudo stepNN` (`sudo /opt/recover/stepNN` also works)
   - Finally, run `curl` on front01 10 times in succession and confirm that every response is 200

## Why investigate this area?

With several simultaneous failures, fixing them in the order they catch your eye risks irreversible damage.
First, inventory the system through observation without changes and protect anything that cannot be recovered if lost.
Then address the foundations causing other problems, such as connectivity, licensing, and hardware.
If aggregate results are consistently wrong, suspect the path used to read the data, including memory, rather than just the data itself.

## Common pitfalls

- Directly rewriting data files that appear corrupted. If the read path is faulty, the data will appear corrupted again even after a correction
- Disabling a memory bank or restarting before preserving the ledger
- Mistaking a command failure during a network interruption for incorrect command syntax
- Proceeding through recovery steps without `--check`
