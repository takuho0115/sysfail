# L024 Order confirmation emails are not arriving

1. On mq01 (ops; use sudo for administrative operations), inspect the queue
   - `mqctl -p /mail list_queues name messages consumers` (do not add `sudo`; it removes the connection destination setting)
   - Is the message count growing? How many consumers are there?
   - If it reports that it cannot connect to cloud01, the simulated queue server is running on mq01 itself. Specify the destination with `SIM_CLOUD_URL=http://mq01:8500 mqctl -p /mail list_queues name messages consumers` (a known issue in this environment)

2. If there are 0 consumers, move to the consumer host, worker01 (ops)
   - Use `systemctl status mail-worker` to check whether it is running or has hit its restart limit
   - Read the connection failure message with `journalctl -u mail-worker -n 20 --no-pager`

3. Find the worker's configuration file and read its connection destination
   - Trace the unit or the program it launches to find the configuration it reads under /etc/mailworker/

4. Compare the destination name in the log with the names that actually exist on the queue server

5. After correcting it, restart the worker and check on mq01 that the message count is falling

## Why investigate this area?

Mail not arriving while queue memory grows means that messages are entering the queue but not leaving it.
With 0 consumers, the problem is that the consuming side cannot connect, rather than the queue itself. The worker's logs explain why the connection fails.

## Common pitfalls

- Emptying the queue to reduce memory usage. That loses mail and is prohibited by the completion conditions
- If the worker has stopped after hitting its restart limit, `restart` alone may not start it even after correcting the configuration. Use `systemctl reset-failed` in between
- Overlooking names in the log and configuration that differ by only one character because you did not compare them carefully
